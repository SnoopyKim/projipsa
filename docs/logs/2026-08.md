## [2026-08-03] update | Purpose restated and documentation restructured

- found: a README review compared the README against the shipped tree, both
  manifests, the three shared workflows, and this memory tree
- restated: the Maker corrected the project's purpose. Projipsa exists so that
  project understanding survives the session and substantial work can be
  delegated against it; the memory is the durable shared state that delegated
  work runs on. Cross-host support is a distribution constraint that follows,
  not the goal. `wiki/project/overview.md` had recorded the constraint as the
  purpose, which is the framing the README inherited
- recorded: the design lineage the Maker named — the LLM-wiki pattern for the
  memory layer, and agent loop and multi-node agent graph design for the
  delivery layer, where Projipsa's contribution is where the shared state lives
  after the run ends. Cited by URL rather than copied, per the public-root rule
- changed: `README.md` rewritten around purpose, install, and usage. Install
  moved from 83% down the page to the top, the plugin version is stated, and a
  five-minute onboarding walkthrough was added
- added: `CONTRIBUTING.md` now holds repository layout, adapter structure, the
  validators, and the publishing checklist
- removed: the v0.3 invocation migration table, which addressed a migration
  from a version that was never listed in a marketplace
- fixed: three README claims that had drifted. It asserted that
  `validate_memory.py` rejects a pointer block naming a different root, which
  [open questions](../wiki/questions/open-questions.md) records as a reproduced
  defect; it described the package validator's scan as the shipped tree and
  README "nothing else", which predates the root marketplace manifests; and it
  never documented why neither host may use a `skills/` directory
- removed: both vocabulary checks in `scripts/validate_package.py` — a
  banned-word scan over every shipped file, and a required-phrase check on the
  plugin description. A request to avoid one word had become a regular
  expression, while none of the drifted claims above were covered by any check.
  The Maker's standing constraint is that the package validator carries no
  semantic or vocabulary rules; documentation carries the concept
- amended: the [ship boundary decision](../wiki/decisions/2026-07-30-plugin-ship-boundary.md)
  carries a dated amendment rather than an edited Decision section, because its
  original scan description was accurate when written
- updated: `wiki/project/overview.md`, `wiki/project/current-state.md`,
  `wiki/questions/open-questions.md`
- validation: `scripts/validate_package.py` passes, 35 tests pass, and the
  rewritten README was checked against `validate_readme`'s whole-token rule for
  all six host invocations
- not done: no implementation file outside `scripts/validate_package.py` was
  touched, and no release was made

## [2026-08-11] fix | Outsource verification made QA-oriented in 0.3.2

- found: real Project-mode use produced a substantially correct contract but
  allowed implementation-authored helper tests and partial execution paths to
  support broader passing claims
- decided: verification starts from the service user, artifact consumer,
  operator, or QA perspective and traces the actual user or data path rather
  than following implementation abstractions
- decided: preservation prohibitions become negative acceptance criteria when
  adjacent work could violate them; risk-shaped cases are planned before
  implementation rather than exhaustively multiplying every input combination
- changed: added the step-loaded Outsource `verification.md` reference with
  evidence suitability, fail-closed verdicts, verifier independence, and
  code/data/operations/document adapters
- changed: Delivery Contract and delivery-page templates now separate planned
  and observed evidence, classify evidence as `direct`, `proxy`, `reported`, or
  `not_run`, and keep execution status, verification status, and Maker decision
  independent
- clarified: incomplete verification may move to Maker review, but Maker
  acceptance or terminal handoff cannot rewrite the technical verdict or turn
  an unexecuted path into a passing claim
- changed: version bumped from 0.3.1 to 0.3.2 in both host manifests and README
- added: two package-contract tests preserve the new verification reference
  and delivery state surface, increasing the suite from 35 to 37 tests
- updated: the evaluation-harness open question now covers workflow behavior
  as well as Skill triggering because static tests cannot judge evidence fit
- decision: wiki/decisions/2026-08-11-qa-oriented-verification-claims.md
- validation: package validator, 37 tests, memory validator over 7 maintained
  pages, `claude plugin validate ./plugins/projipsa --strict`, and
  `git diff --check` pass
- not done: no install refresh, marketplace listing, or release
